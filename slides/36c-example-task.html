A well-specified task

Task: Add retry handling to the HTTP client

Objective: Retry network failures when calling the QService 2.0 API.

Scope:
- Modify src/http/client.ts.
- Preserve the existing public interface.
- Do not modify unrelated API consumers.
Workflow tips:
- Read unstaged files; I left some hints in the code.
- Investigate if we have something similar in place.
- Any major blocker pause the task, report back and wait for instructions.

Requirements:
- Retry on HTTP 429, 502, 503, and 504 AND Qservices URLs.
- Maximum 3 retries.
- Logger, analytics, etc etc etc
- NEVER retry non-idempotent requests (by default).

Acceptance criteria:
- Unit tests cover successful retries and retry exhaustion.
- Existing tests pass.
- TypeScript compilation succeeds. Docker build working, no new warnings. Stone soup.

On Completion: Summarize changed in bullet points, test cases, and remaining limitations.

  2. Scope —
  3. Requirements — Decisions made up front
  4. Acceptance + completion — how to prove. What to report back
~60s. Four clicks, top to bottom: each one reveals a block of the task and its legend entry; a fifth click shows the brown "workflow tips" (how I want it to work, not part of the spec). Every line removes a decision the agent would otherwise make for you: which file, which status codes, how many retries, what "done" means. Note "Do not retry non-idempotent requests": a constraint nobody thinks to ask for until it bites. Same idea as the prompt template later, written for one task.
